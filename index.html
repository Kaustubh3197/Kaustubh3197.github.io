  • Overview

    Which middleware should carry data inside a software-defined vehicle?

    I scored eight in-vehicle protocols on latency, determinism, QoS support and ecosystem maturity, then built the top three as proof-of-concept implementations on an identical simulated ADAS workload.

    What I did

    • Scored 8 candidate protocols using a multi-criteria decision analysis (MCDA)
    • Built matching proof-of-concept implementations in OpenDDS, vSomeIP and Zenoh
    • Ran the exact same simulated ADAS setup (7 software components with the same timing limits) on all three, so any difference in the results comes from the middleware alone

  • Overview

    The perception stage of a four-stage university V2X project.

    Radar data, live from a perception kit or replayed from rosbag files, is first filtered to remove false detections, then visualized in RViz next to an ego-vehicle model, and finally converted into standard Collective Perception Messages (CPM).

    What I did

    • Filtered radar false positives using confidence-score and distance thresholds
    • Classified objects as cars or pedestrians and rendered them as live RViz markers
    • Converted the filtered objects into CPM messages using roughly 130 custom ROS message definitions aligned to the ETSI ITS standard

    Type

    University team project, perception stage

  • Overview

    Two independent circuits on one car.

  • Overview

    Tests that use an online shop the way a customer does: logging in, sorting and opening products, managing the cart and checking out.

    The critical flows are covered with both Playwright and Selenium, and the full suite runs on every push, every pull request and every night.

    What I did

    • Built 16 Playwright tests and 5 Selenium tests, including negative and price-calculation checks
    • Structured the suite with the Page Object Model, chained pytest fixtures and data-driven parametrized tests
    • Set up a GitHub Actions matrix that runs the suite on Chromium, Firefox and a mobile viewport, keeping reports, screenshots and traces for failures
    • Extended the framework with a new page object and tests for the product details page

  • Overview

    A small task-tracking app used to build a complete delivery pipeline.

    Every pull request is checked automatically. Every merge to main is linted, tested on three Python versions, browser-tested, packaged and smoke-tested in Docker, published, deployed to Render, and then the live site is checked for the new version.

    What I did

    • Built a Flask app with 31 unit, API and Playwright tests, including a test I added that caught a wrong change to the title-length rule and stopped it from being merged
    • Designed a gated six-job GitHub Actions pipeline: lint, matrix tests, browser tests, Docker smoke test, image publishing and deployment
    • Deployed through a secret deploy hook with auto-deploy and PR previews disabled, so only tested code on main can go live
    • Ran a production incident drill: diagnosed a production-only crash from server logs, restored service with a rollback, and fixed main with a revert

    Type

    CI/CD pipeline with live app
